# Harness requirements and acceptance scenarios

Status: **[accepted baseline](harness-glossary.md#terms)**, 2026-10-12: the architecture was accepted as amended in [DEC-009](../decisions/DEC-009-architecture-acceptance-and-remaining-dispositions.md). First proposed 2026-10-01. Amended 2026-10-12 for [DEC-008](../decisions/DEC-008-adversarial-review-dispositions.md) and the [adversarial review](../research/adversarial-design-review.md), adding FR-29–41 and NFR-14–15, and for DEC-009, adding FR-42–43; each amendment changed the rows it touches. Names and values follow the [glossary](harness-glossary.md). Applies to the [harness proposal](audit-harness.md) within the accepted [operating envelope](../decisions/DEC-002-harness-operating-envelope.md) and [confirmation evidence policy](../decisions/DEC-004-confirmation-evidence-policy.md). “Must” specifies required future behavior if this design is implemented; it does not claim implementation or successful runtime testing.

Priorities: **core** is required before accepting audit conclusions through the harness; **v1** completes the first proposed product; **later** is explicitly deferred. Core work can be performed manually through structured records before all agent assistance exists. Under DEC-008 (Q-020), a walking skeleton with minimal machinery delivers core requirements first. Mechanisms whose only purpose is concurrency, remote execution or long-lived services are deferred until an observed failure justifies them; see [deferred mechanisms](harness-state-and-execution.md#deferred-mechanisms). DEC-008 fixes that the skeleton keeps these invariants and includes the Q-016–019 choices; the rest of the first build's functional scope belongs to the implementation handoff. Future acceptance scenarios are design checks, not a new test suite for this specification-only repository.

## Functional requirements

| ID | Priority | Requirement | Observable acceptance scenario |
|---|---|---|---|
| FR-01 | core | Freeze source, dependencies, effective build settings, scope and environment identity | A dirty local checkout produces a content-addressed snapshot including selected changes; missing deployment data produces a source-only limitation |
| FR-02 | core | Require human scope, threat-model, data-policy and budget decisions | An agent-requested new chain, permission or provider cannot execute under the old scope |
| FR-03 | core | Run baseline builds and structural analysis in isolation and record partial/unsupported results | A failed build cannot appear as a clean analyzer result; an unresolved proxy target appears as a model gap |
| FR-04 | core | Maintain separately inspectable DESIGNED and IMPLEMENTED behavior, keeping intent, implementation, assumptions, guarantees and unknowns distinct and source-linked | Documentation-first design is refined through auditor input and applicable evidence; conflicts and reconstruction lineage survive summarization |
| FR-05 | v1 | Support progressive modeling and repeated DESIGNED/IMPLEMENTED comparison by complete flows and trust boundaries | Each lens records correspondence, comparison coverage and discrepancies; equivalent abstractions are not reported as bugs, and deeper withdrawal failure-path review can reveal a new deviation |
| FR-06 | v1 | Route focused clarifications with owner, consequences, evidence, priority and affected work through a capacity-limited queue that coalesces duplicates | An unknown token behavior blocks dependent accounting conclusions while unrelated authorization work proceeds; a full clarification queue holds lower-priority clarifications without dropping them; client questions export as one batch |
| FR-07 | core | Admit only human-approved, bounded work authorizations (`intake`, `exploration`, `batch`, `revalidation`, `method_evaluation`) with current revisions and budgets | Agents draft and iterate scenarios under approved investigation questions and constraints without a required co-authoring checkpoint; an added investigation question remains proposed, while a follow-up into another guarantee that needs nothing new and changes no meaning runs as a linked variant (DEC-009, Q-026); L0 seeding runs only under an `intake` authorization |
| FR-08 | v1 | Apply role-specific context and tool grants; record context exposure and challenge independence | A challenger starts without the author's rationale or the provisional statements on the challenged path, then reviews the actual fixture; provenance records both stages and whether the same model or provider was used |
| FR-09 | core | Support hypotheses, properties and scenarios through a common investigation contract that records scenario variants | Each method returns support, refutation or an unresolved result; each scenario variant has its own outcome and lineage; inner experiment jobs share the parent limit |
| FR-10 | core | Separate raw tool outputs, interpretations, job state, proof status and human disposition | Compilation failure, no observed violation, counterexample and human acceptance remain different records |
| FR-11 | core | Require semantic review and adequacy evidence for consequential generated properties | A campaign whose useful actions all revert cannot count as adequate; a changed assertion requires new review. Agents classify which changes are consequential and the challenger reviews that classification (DEC-008, Q-014; an accepted residual risk) |
| FR-12 | core | Preserve exact experiment inputs, fixtures, commands, tool identities and limitations | A reviewer reconstructs the package without access to the originating conversation or hidden scratch files |
| FR-13 | core | Replay executable evidence in a clean environment and review attacker realism against the engagement's attacker charter | A test that relies on governor impersonation cannot confirm a permissionless exploit without a valid capability argument; a negative result that depends on environment reads is labelled environment-sensitive |
| FR-14 | v1 | Group duplicates and related causes without losing provenance or dissent | Merging two leads preserves both origins; a proposed bug chain remains a separate investigable claim |
| FR-15 | core | Restrict acceptance, final severity, closure and report approval to the human, through decisions bound to displayed revisions | The auditor reviews one combined packet after testing and challenge, with evidence first for potential High/Critical decisions; forged, stale, undisplayed or bulk approvals are rejected; rationale authorship is recorded |
| FR-16 | core | Retain rejected, bounded-negative, triaged, disputed, deferred and blocked work with reasons and evidence scaled to potential impact | Exhausted runtime yields `no_finding_within_bounds` or unresolved exposure, never `rejected`; a refutation links the decisive countercondition; a High/Critical executable rejection without a violating positive control is refused |
| FR-17 | core | Re-evaluate positive and negative conclusions through dependency probes when premises or code change, and review each revision forward from its diff | Removing a guard reopens its rejected lead as `affected`; unchanged probes carry conclusions forward under a labelled attestation; unknown reach is flagged `possibly_affected`; a fix that adds a new function produces an unreviewed-change gap |
| FR-18 | core | Pause and cancel jobs with bounded retries and reconcile uncertain external calls; add leases and fencing when concurrent or remote workers exist, and idempotency records when clients retry over a transport that can lose responses | In the walking skeleton, pause terminates the process group and leaves one recorded attempt, and a provider timeout yields `outcome_unknown`; once concurrent workers exist, late output from an expired attempt cannot replace current state |
| FR-19 | v1 | Constrain new discovery to the auditor's review capacity | A full review queue pauses new discovery and presents a batch summary without discarding admitted work |
| FR-20 | core | Assess fixes on a separate revision through attack and legitimate-behavior checks, client responses and a scoped review mode | A patch that blocks the exploit but disables every withdrawal is reported `regressive`; a declined fix is `acknowledged` with the client's response; code outside the diff and the listed findings is labelled not re-reviewed |
| FR-21 | core | Generate confirmation reports and PoC packages from explicit decisions, with evidence routes scaled to potential impact | Every reported finding resolves to a current acceptance record and evidence; an evidence exception is labelled and carries its attempt history; every PoC is a non-broadcastable test that includes the fork state it touches |
| FR-22 | core | Include scope, gaps, unresolved exposure, assumptions and trust premises, failures and limits in closure, checked against a controller-computed required set | The auditor can close a time-limited engagement with limitations; missing work cannot be represented as completed review; an omitted required item needs an audience or redaction reason |
| FR-23 | v1 | Capture source-backed engagement lessons with counterconditions and review state | A rejected analogy is retrieved with its failure conditions; no memory can authorize a new finding |
| FR-24 | core | Isolate engagements, the agent tool and network egress, and control reuse/export destinations | A query or export from engagement A cannot retrieve B; the agent tool's memory and transcripts stay inside the engagement; a sandboxed test reaches no network destination except the RPC gateway; within the harness, reusable knowledge moves between engagements only through the mechanism library, which only `record_transfer` decisions write (DEC-009, Q-022) |
| FR-25 | v1 | Record comparable outcome, cost, human-work and decision-quality measurements | Duplicate floods, unresolved candidates and deferred work are visible in the evaluation denominator; seeded canary packets measure whether the auditor catches invalid claims |
| FR-26 | v1 | Version workflow, prompt, retrieval and tool changes with evaluation and rollback | A proposed improvement fails a retained case, judged over several runs of a stochastic model, and can be rolled back without rewriting previous audit results; adoption follows the held-out comparison (DEC-009, Q-024) |
| FR-27 | later | Add other ecosystems, remote worker fleets, semantic indexes or further analysis engines through adapters | An adapter must declare supported semantics, result types, limits and compatibility scenarios before use |
| FR-28 | v1 | Track applicability and evidence for selected baseline controls alongside protocol-specific investigations | Each relevant checklist item has examined evidence or a visible gap; completion is not presented as proof of security |
| FR-29 | v1 | Seed the engagement KB automatically in bounded rounds (DEC-005) | After an intake round, a partial seed with explicit gaps is available; no seeded statement becomes reviewed semantics without a human decision |
| FR-30 | v1 | Represent flows as state machines with KB diagrams bound to their record dependencies (DEC-005) | A changed transition marks its diagram `affected`; regeneration shows a semantic delta and grants no re-review |
| FR-31 | v1 | Offer repeatable, resumable explorations from any stage, defaulting to a connected walkthrough with optional checkpoints (DEC-005) | An exploration resumed after a premise change shows what changed before continuing; a skipped checkpoint records neither mastery nor failure |
| FR-32 | core | Start investigations only after broad orientation and a recorded review of the relevant flow (DEC-005) | `authorize_work` refuses a batch whose relevant flow has no `record_flow_review` decision, while other flows remain visible as gaps; a linked variant may enter an unreviewed flow, and its packet flags the claim ([DEC-010](../decisions/DEC-010-linked-variants-into-unreviewed-flows.md), Q-027) |
| FR-33 | core | Apply a default attacker charter that the auditor narrows per engagement, and report the trusted-role premise ([DEC-008](../decisions/DEC-008-adversarial-review-dispositions.md), Q-015) | An ordering or flash-loan variant runs without an interrupt unless the engagement excludes it; "privileged roles trusted" appears in the report's assumptions |
| FR-34 | core | Derive the scope inventory deterministically from compiler artifacts, verify vendored dependencies and track the auditor's review coverage | A modified vendored library is flagged as modified; closure lists in-scope functions that map to no unit and those the auditor never reviewed |
| FR-35 | v1 | Generate leads per audit unit through declared generators with coverage status, including applicable standards, upstream diffs, the project's own test suite and mechanism-library retrieval | A vault that matches its documentation still receives ERC-4626 conformance and rounding leads; an admitted library mechanism that matches a component class yields a lead carrying its counterconditions; a batch proposal shows which generators ran |
| FR-36 | v1 | Track cross-flow compositions and system-wide invariants as audit units | Two flows writing the same store produce a composition item with a review status; solvency appears as a system-invariant unit |
| FR-37 | v1 | Record conservation relations, units and decimals, and rounding direction for accounting flows | A rounding-direction table names who benefits from each arithmetic operation in a share conversion |
| FR-38 | core | Defend analysis integrity against steering, display deception and environment-sensitive target behavior | An instruction addressed to AI auditors is flagged at intake; a bidirectional-control character is rendered visibly; a branch on `tx.origin` is flagged and replayed with realistic values |
| FR-39 | core | Record the auditor's typed input verbatim outside the model, and accept agent interpretations only through batched confirmation ([DEC-008](../decisions/DEC-008-adversarial-review-dispositions.md), Q-018) | An agent paraphrase cannot become an auditor clarification; each interpretation is confirmed, edited or rejected individually on the trusted decision screen |
| FR-40 | core | Surface unreviewed agent premises in each decision's dependency closure | A rejection that depends on an unreviewed seeded statement is recorded as conditional on it unless the auditor reviews or accepts it |
| FR-41 | v1 | Capture commands the auditor runs into the evidence record | A test the auditor runs in their own terminal enters as an auditor-run artifact, with a receipt from the trusted runner or an explicit untrusted-receipt label |
| FR-42 | v1 | Maintain a curated cross-engagement mechanism library of public entries and the auditor's sanitized lessons ([DEC-009](../decisions/DEC-009-architecture-acceptance-and-remaining-dispositions.md), Q-022) | An agent cannot write the library; a lesson transfer without the auditor's confirmations that client details are removed and that reuse is permitted is refused; no entry names its source engagement; an engagement retrieves an admitted entry with its counterconditions |
| FR-43 | v1 | Offer an optional expectations pre-step and read-first mode, and record when the auditor's intent was captured relative to the first recorded presentation of its audit unit's implemented behavior ([DEC-009](../decisions/DEC-009-architecture-acceptance-and-remaining-dispositions.md), Q-023) | Skipping the pre-step blocks no work; intent captured before that presentation, including during read-first mode, is `before_walkthrough`, and later intent is `after_walkthrough`; viewing a seeded preliminary diagram counts as a presentation; a comparison that relies on `after_walkthrough` intent shows the tag |

## Non functional requirements

The numerical values below are **proposed acceptance targets**, not measured performance or operator-approved spending allowances. An implementation trial may revise them through a recorded decision. Enforcement invariants are stricter than convenience targets.

| ID | Requirement | Proposed observable target or invariant |
|---|---|---|
| NFR-01 | Human authority | Zero accepted findings, semantic approvals or final reports created through agent-only transitions in adversarial acceptance scenarios |
| NFR-02 | Integrity and consistency | Every acknowledged metadata change has an atomic record/event commit; referenced eligible artifacts have verified hashes; stale writes conflict visibly |
| NFR-03 | Reproducibility | Every executable confirmed finding has a clean replay receipt against its declared snapshot; unavailable replay remains explicit |
| NFR-04 | Isolation and confidentiality | No execution-worker or agent-tool access to provider keys, signing keys, unrelated engagement data, live write RPC or unapproved network destinations; denied attempts are recorded |
| NFR-05 | Recoverability | No loss of acknowledged decisions in crash/restore scenarios; uncertain in-flight work remains unresolved until reconciliation; corrupted state fails closed |
| NFR-06 | Bounded resource use | Every attempt has finite runtime, output, memory, process and spending bounds; reservations cover concurrent work and uncertain billed calls; provider accounting uncertainty is surfaced |
| NFR-07 | Responsiveness | On the pilot workstation, control acknowledgement within 2 seconds at p95; dispatch stops immediately after committed pause; worker stop or explicit failure-to-stop visible within 10 seconds |
| NFR-08 | Review usability | Scope, strongest evidence, counterargument, gaps and next action visible in one short packet; full evidence reachable directly; potential High/Critical packets show evidence before the proposed disposition; deceptive characters rendered visibly; every interruption identifies the dependent work; decision controls work by keyboard and expose textual status to assistive technology |
| NFR-09 | Observability | Every invocation records input identity, tool/mode/version, time, result/error, cost category and output location; truncated or lost output is flagged |
| NFR-10 | Portability | Export contains documented schemas, manifest and portable artifacts; reports and decisions remain inspectable without a model provider or the original agent host |
| NFR-11 | Retrieval correctness | Context records include source and revision; relevant disputed status and freshness survive summarization; indexes can be rebuilt from authoritative records |
| NFR-12 | Maintainability | Tool/provider adapters use the same contract for capabilities, errors and evidence; unsupported versions fail explicitly; migrations retain backups and prior schemas |
| NFR-13 | Honest assurance | No aggregate security percentage, model agreement, visit count, passing test count or benchmark label is presented as proof of whole-system safety; `triaged_out` supports no assurance claim; `no_finding_within_bounds` is never presented as refutation; mechanical carry-forward is labelled as such |
| NFR-14 | Decision quality | In pilots, seeded canary packets (invalid claims with plausible narratives, and valid claims with weakened counterarguments) are caught at a rate the operator sets before the pilot; inspection depth and dwell time are reported but are never approval signals |
| NFR-15 | Decision load | A decision inventory gives the expected human decisions per engagement-day by kind; the pilot measures actual counts and active minutes against a ceiling the operator sets before the pilot |

Measure p95 only with enough timed interactions to make it meaningful; otherwise report raw samples. A failed stop deadline blocks additional overlapping dispatch and triggers operator attention. The pilot defines representative workstation resources, corpus size and workload before measuring responsiveness.
